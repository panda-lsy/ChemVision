# 参赛技术报告（草稿）

## 问题背景与目标

化学学习需要在名称、分子图、结构文本与概念解释之间转换。自然语言讲解难以直接完成可编辑的结构操作，而专业结构编辑器通常需要用户另行组织教学问题。ChemVision 将这些操作放入同一客户端，以便学生查询、检查、修改结构并围绕同一结构继续学习。此处描述的是产品设计动机，尚无用户访谈或教学实验支持普遍性结论。

核心目标用户为化学课程学生及其指导教师。当前优先验证单人学习流程，不声称已有学校部署或合作机构。

## 技术方案

1. **结构作为接口**：名称和图像最终转换为 SMILES；编辑器输出仍为 SMILES。图形展示依赖 SmilesDrawer/Ketcher，数据库返回分子式和分子量。模型生成文本与图形绘制分离，便于复查来源。
2. **受约束名称解析**：中文名称先通过提示词调用外部 LLM 做规范化，之后查询 PubChem，失败时尝试 OPSIN。用途推测模式先生成名称候选，再经相同数据库/解析器检索。不是“任意模型输出即认定分子正确”。
3. **图像识别接入**：图片以 multipart 传至 DECIMER 包装服务，结果做轻量语法/完整度评分，再查询候选。完整度是规则分数，不能解释为识别准确率或化学完整性概率。
4. **显式教学流程**：`TaskPlanner` 选择预设任务；`AgentOrchestrator` 按序调用工具，通过 `@slot.field` 传递结果；关键识别或 LLM 失败会中止，其他查询可能降级。步骤状态可用于界面解释和失败排查。
5. **记录驱动建议**：真实查询/扫描写入 Hive；知识点掌握度以行为规则汇总。诊断/规划将相关统计及薄弱点传入 LLM。出题与错因内容生成不应等同于真实作答，本轮已去除无依据的自动成绩写入。

## 可验证的工程差异

本项目的差异在于“结构操作—工具链—教学上下文”的衔接，以及通过回归测试约束数据错误和失败状态。可指出具体代码中的输入/输出、缓存键、工具引用、持久化边界及用户操作入口。

本轮典型修复说明：旧缓存将全部查询小写化，使 `c1ccccc1` 与 `C1CCCCC1` 混淆；新反向结构缓存保留大小写并换命名空间，避免读取旧歧义条目。这个修复体现化学表示的领域约束，不是新的化学算法。

不得使用“首创中文命名模型”“自研 OCSR”“达到专业软件精度”“LLM 全自主规划”“严格价态证明”“自动证明分子式一致”等尚无支撑的表述。

## 场景价值与验收

目标闭环为名称查询→结构图→编辑→收藏→“AI 讲解此结构”→知识点与查询记录→新会话学情诊断。入口传递精确 SMILES，用户确认发送后才请求 AI，避免仅把中文问题交给自由聊天。

验收包括：正确分子式、结构一致性、收藏可重开、工具步骤可见、失败不会伪装成功、诊断读取真实记录。截图、实际服务配置、模型版本和耗时见 [证据文件](06-evidence.md)。本轮离线工具桩不能证明模型正确率；真实公共化学服务测试也不能证明教学效果。

## 局限与风险

- 轻量 SMILES 检查不是 RDKit 等严格化学验证；`isValid` 不应理解为全部化学性质正确。
- 知识点匹配依赖字符串，可能混淆醇/酚、醛/酮等；需人工审阅与后续结构级算法。
- 反应补全没有建立元素/电荷守恒强校验或来源真实性保证，不作为主展示承诺。
- 中文规范化与图像识别受模型、网络、配额、CORS 影响；未完成全离线部署验证。
- 画像启发式没有教育测量有效性证据，旧版本可能已写入推断成绩，不能静默当成真实答题数据。
- 开源许可、SDK、素材来源及参赛主体仍有人工确认项。
